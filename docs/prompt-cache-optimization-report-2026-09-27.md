# 输入缓存优化报告

日期：2026-09-27<br>
对象：Harness Agent 1.4.3<br>
状态：本文保留实施前诊断；后续源码升级与验收见[升级记录](prompt-cache-upgrade-2026-09-27.md)<br>
范围：输入缓存、上下文管理、摘要请求与统计展示

## 1. 结论

当前缓存能力已生效，但长任务中的历史重写与摘要策略削弱了复用效果。优先优化上下文生命周期，而非继续加长固定 Prompt 或仅调整 cache key。

主要发现：

1. 达到上下文阈值后，旧工具结果被替换为证据引用，破坏已发送的历史前缀；这条分支未记录正式压缩事件。
2. 正式摘要重建前部历史，使后续请求需要重新积累缓存。
3. 最新任务的四次模型摘要均未被采用，却消耗了 132,309 个零命中输入 tokens。
4. 当前保存的 Profile 使用“70% 触发、压缩后允许 80%”配置，没有保证压缩后回落到触发线以下。
5. 长推理输出放大上下文压力；摘要请求与主任务共用模型，却仅有 2,048 tokens 输出额度。

优化目标应同时包含：降低未命中输入、减少无效摘要、保持任务完成质量与证据完整性。命中率不是唯一目标。

## 3. 原因分析

### 3.1 旧工具结果替换破坏缓存前缀——已离线复现

在 `pi-agent-bridge.ts:718–722`，达到估算阈值后，程序把较早的工具结果替换为 `evidenceId`。如果替换后低于阈值，立即返回，不触发 `onCompaction`。

离线轨迹包含 14 次模拟请求：

| 请求序号 | 首个变化消息索引（从 0 开始） | 原工具消息字符数 | 替换后字符数 |
| -------- | ----------------------------: | ---------------: | -----------: |
| 9        |                             3 |            6,120 |          146 |
| 14       |                            13 |            6,120 |          146 |

两次都改写了此前发送的历史，正式压缩事件数却为零。因此，“没有压缩事件”不等于“缓存前缀稳定”。当前短轨迹稳定前缀测试未覆盖这一阈值分支。

### 3.2 正式摘要靠前插入，重建后缀——源码与日志一致

`pi-agent-bridge.ts:740` 重建历史为 `first → summaryMessage → recent → base`。摘要变化发生在较前位置，先前的后续历史不能继续作为相同前缀复用。

最新任务四次正式压缩后，首个主调用均只命中 4,352 tokens。第一次压缩前后的数据为：

- 压缩前：命中 43,264 / 输入 52,400，约 82.56%。
- 压缩后：命中 4,352 / 输入 16,446，约 26.46%。

必要压缩本身有价值；问题在于重写频率、压缩目标以及是否保留足够有效证据，不能为了命中率永不压缩。

### 3.3 摘要预算与推理模式不匹配——高度支持，需补充分项日志

`summarizeOldContext` 使用主任务模型，输出上限为 2,048 tokens，收集正文并校验 JSON。

最新四次摘要：

- 输出均达到 2,048 tokens。
- 全部 `deterministicFallback=true`，即最终使用程序摘要。
- 两次 2,048 tokens 全部用于推理，没有留下最终正文额度。

这些数据支持“推理占用摘要输出预算，导致摘要无法完成或通过校验”的判断。仍需区分输出截断、空正文、格式错误及其他异常，不能把所有回退都归为同一种错误。

DeepSeek 官方说明，思考模式默认启用；带工具的请求需要按协议续传推理内容。因此应管理推理生成预算，不能简单删除历史推理。[官方思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)

### 3.4 保存的 Profile 未形成压缩回落空间——配置已确认

| 参数                    | 采样时保存值 |           当前源码默认值 |
| ----------------------- | -----------: | -----------------------: |
| compactAtRatio          |         0.70 |                     0.80 |
| maxAfterCompactionRatio |         0.80 |                     0.45 |
| retainRecentTurns       |            2 |                        2 |
| workingContextTokens    |       未设置 | 未设置时使用最多 128,000 |

在模型容量至少为 128,000 的条件下，旧配置对应 89,600 触发、压缩后允许 102,400。后者高于前者，无法保证下一次请求离开压缩区域。实际模型容量更小时按更小值计算，比例矛盾仍然存在。

源码没有强制校验压缩后比例小于触发比例。只修改新默认值不会自动修正已保存的 Profile。

### 3.5 放大因素

- 主调用输出约 94.5% 为推理，单次最高报告 63,011 个推理 tokens；续传可能显著增加上下文压力。
- 估算器设有较保守的字符密度下限，应使用实际用量校准并检查不同语言、工具数据及图片的误差，不能仅以字符串长度认定已到模型硬上限。
- 工作预算、模型真实容量和剩余输出空间是不同约束，不宜简单增大上下文窗口来掩盖频繁重写。

统计加权公式、缓存字段覆盖和 cache key 的稳定身份设计均未发现是本次首要原因。

## 4. 优化方案与优先级

| 优先级 | 工作项             | 建议措施                                          | 预期作用                     |
| ------ | ------------------ | ------------------------------------------------- | ---------------------------- |
| P0     | 摘要成功率         | 独立设置摘要推理策略，校验最终 JSON，记录回退原因 | 减少消耗输入后仍被丢弃的摘要 |
| P0     | Profile 迁移与校验 | 对旧配置建立版本化迁移，保证压缩目标低于触发线    | 避免压缩后立即再次触发       |
| P1     | 上下文重写策略     | 首次发送限制工具结果体积，必要时一次性批量重建    | 减少零散历史改写             |
| P1     | 可观测性           | 记录工具裁剪、前缀变化、摘要结果与阈值            | 让缓存骤降能够归因           |
| P2     | 模型与预算校准     | 分离主任务和摘要预算，验证真实容量及估算误差      | 降低长推理带来的上下文压力   |
| P2     | UI 展示            | 明确区分总命中率、主调用和辅助调用                | 避免混合口径误读             |

### 4.1 P0：摘要路径

- 对已确认支持的 Provider/API，摘要采用明确的非思考模式；如协议不支持，不发送未经验证的参数，使用可配置的专用摘要模型或程序摘要。
- 首轮方案保留 2,048 tokens 正文目标，先解决推理占用与输入整理，再根据成功率决定是否增加额度。
- 摘要输入保留目标、约束、证据 ID、已完成操作和未完成事项；按完整记录裁剪，避免直接截断序列化文本导致信息边界不完整。
- 验证 JSON 字段、类型、长度和关键任务信息，禁止把 DSML、工具调用文本或无正文响应当作摘要。
- 同一历史段摘要失败后回退一次，记录原因；该运行中后续摘要优先采用程序摘要，避免同类失败反复消费预算。主任务调用不受此降级规则影响。
- 确保摘要调用的输入、输出、缓存、耗时和费用继续计入真实预算，不通过隐藏辅助请求改善表面指标。

### 4.2 P0：配置迁移

建议试运行采用源码已有的 `compactAtRatio=0.80`、`maxAfterCompactionRatio=0.45`。这是一组试运行默认值，不是所有负载的最优配置。

- 新建、编辑及导入配置时校验 `maxAfterCompactionRatio < compactAtRatio`。
- 对旧版已知默认配置做一次性版本迁移，保留原值以便回退。
- 自定义有效配置保持不变；自定义无效配置明确提示，并使用可记录的有效运行参数，避免静默覆盖用户偏好。
- 迁移只影响新 run；不在活动运行中切换上下文策略。
- 保留运行时的硬容量检查。降低压缩目标后，若必须保留的任务信息仍放不下，应明确报告，不能静默丢弃用户要求。

### 4.3 P1：稳定前缀与工具结果管理

- 保持 system、工具契约和已发送历史在一次上下文周期内稳定；动态状态继续尾部追加。
- 工具结果首次进入模型前就采用有界摘要、关键片段和证据 ID；完整结果保留在证据存储，按需读取。
- 已发送结果不再随着滚动窗口零散改写。需要释放容量时进行一次可观测的批量重建，并将上下文压到目标比例。
- 保留工具调用/结果配对、真实错误信息和必要推理状态。读取证据必须仍可定位原结果。
- 压缩后尽可能保留固定前缀，不将每轮变化的摘要提升为 system/developer 内容。必要重建造成的缓存下降应记录为正常成本。

### 4.4 P1：观测与展示

建议在完成 Provider 适配、即将发送请求的边界统计变化，避免仅比较内部对象误判：

| 指标       | 内容                                                                         |
| ---------- | ---------------------------------------------------------------------------- |
| 请求用途   | main / compaction / review                                                   |
| 前缀稳定性 | 首个变化消息位置、共同前缀长度、变更原因                                     |
| 上下文调整 | tool_prune / full_compaction / resume_rebuild，以及前后估算量                |
| 摘要结果   | accepted / truncated / empty / invalid_json / provider_error / deterministic |
| 配置快照   | 有效工作容量、触发比例、目标比例和配置版本                                   |
| 实际用量   | 输入、命中、输出、推理 tokens，字段缺失单独表示                              |

只保存长度、枚举、范围受限的指纹和必要标识，不新增 prompt、代码、凭据正文日志。共同前缀字符数不是服务端缓存 token 数，必须分开标注。

UI 已有按用途明细，优先强化总指标与主调用的区别，并补充摘要采用率、裁剪次数和未命中输入；不另造一套相互矛盾的统计口径。

| 场景             | 验收要求                                                 |

| 摘要异常         | 截断、空正文、错误格式和服务失败各自分类，回退不循环重试 |
| 旧 Profile       | 迁移可追踪，新旧配置均满足比例关系                       |
| 恢复与工具配对   | 无孤立工具结果；中断操作不被重复执行                     |
| 统计覆盖         | 未知不计为零；总计与分组的输入、命中、输出可对账         |
| 安全及任务质量   | 权限、审批、证据追溯和完成门槛不被弱化                   |

实现阶段执行相关测试、`pnpm typecheck`、`pnpm lint`，并按影响运行全量测试与构建。本报告阶段未实施上述优化，不将既有测试通过等同于优化完成。

### 5.2 真实模型试运行

采用同一仓库提交、任务输入、模型、API、工具集合与预算，优化前后各至少三次独立运行。记录缓存预热顺序、请求间隔和服务端差异；交替运行降低时间偏差。工具结果可先用离线回放验证稳定性，再做真实端到端任务验收。

以下为建议目标，尚未实测，也不构成效果承诺：

- 同等任务完成质量下，未命中输入 tokens 中位数降低至少 20%。
- 摘要采用率达到 90%；摘要调用为零时记为“不适用”，不得记为 100%。
- 超阈值后每次历史重写都有原因记录，覆盖率 100%。
- 不再因无效比例配置导致压缩后仍高于触发线。
- 长任务主调用命中率争取达到 85%，同时总输入不因追求命中率而明显增加。
- 任务完成率不下降，记录耗时和费用；无可靠计费数据时仅报告 tokens，不推算确定金额。

样本较小，初步结果用于筛查方向；扩大样本后才能作稳定性结论。本报告不包含真实模型试运行的执行。

## 6. 实施顺序与回退

1. 补齐观测和固定离线基线，确保能区分裁剪、正式压缩、恢复与供应商缓存行为。
2. 上线摘要策略和 Profile 迁移，先验证摘要采用率与无效输入是否改善。
3. 调整工具结果首次发送与批量重建机制，观察前缀重写频率。
4. 再按真实模型容量、推理输出与任务质量校准工作预算，最后调整 UI 展示。

各阶段独立控制、独立验收。出现上下文超限、工具配对错误、证据丢失或任务完成率下降时，回退对应策略；保留原配置快照和硬容量、权限、预算检查。不要把回退诊断记录或预算统计一并关闭。
