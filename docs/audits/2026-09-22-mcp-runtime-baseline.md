# MCP 接入前的任务运行基线修复

目标：外部 MCP 与项目任务、工具和技能协同。本文只记录已修复的前置运行错误，不代表 MCP 功能完成。

## 已证实的问题

1. 任务引擎和技能推荐请求允许最多 393,216 输出 tokens。上下文压缩器把这个上限完整从模型总上下文中扣除；对于默认 128,000 上下文模型，输入容量变成 1。结果是首次主模型请求之前就压缩失败，技能和工具均不能工作。
2. Parallel 搜索健康检查把任何非空字符串视为有效凭据。带中文占位文字的配置会进入请求路径，技能推荐也没有在配置不可用时启用已有 GitHub 后备检索。
3. 现代任务测试仍要求 8,192 输出，与发布说明中明确要求的 393,216 输出上限不一致。

## 当前修复

- 输入压缩依据工作上下文和模型容量；不再预占全部输出上限。每次主请求及协议修复后的重试根据输入估计计算剩余输出空间；足够大的模型保留 393,216 上限。
- 搜索凭据在网络请求前检查，错误消息不包含密钥；配置健康检查失败时说明原因并使用现有公开 GitHub 搜索。
- 更新旧额度断言，验证输出不能超过用户配置或模型剩余上下文。
- 增加 8 项桥接集成测试：128k 模型（带/不带压缩政策）、1M 模型保留大输出上限、显式 512 小上限、1k 小上下文、服务端报告高于字符估计的用量、中文以及图片输入。前 4 项均执行技能指令、真实工具桥接回合和结果回传；后续测试由模拟服务端独立判定是否超出上下文。
- 原 `skill-session-integration.test.ts` 保持不变，修复后通过，证明原故障不应通过删除或放宽技能断言来掩盖。

## 独立审查后的修正

审查发现：单纯按字符数 / 4 分配几乎全部剩余输出可能低估中文、图片和工具结果；固定预留 1,024 tokens 会拒绝小上下文模型。新增 4 项测试先复现失败，再完成修正。

当前请求预算使用 ASCII 两字符/token、非 ASCII UTF-8 字节、图片尺寸预留，与服务端实际用量校准（含 10% 余量）取较大值。上下文额外预留随模型容量缩小。避免永久按全部 UTF-8 字节作为 token 上限所导致的有效 ASCII 上下文被过度削减。压缩与发送共用纯估算函数，避免长任务通过压缩阈值后又在发送前失败；仅实际请求更新用量校准基数。

这仍是估算而不是各模型专用分词器；未见过的特殊编码、密集 ASCII 和供应商独有图片计费可能偏离估计。不能把通过模拟服务端验证描述为所有外部模型都已经实测。

审查修正后的相关 13 项测试通过（含压缩、图片持续传递和技能恢复）；统一估算后，审批、长任务修复及恢复等 61 项针对性回归通过。最终全量回归 `.cache/mcp-final-runtime-tests.json` 为 453 项全部通过，最新 `pnpm typecheck` 和 `pnpm build` 均通过。
