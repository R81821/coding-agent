# Harness Agent 1.4.0-beta.2

1.4.0 批次一的第二个预发布版本：修复真实运行中发现的三个缺陷，并把持久化从 sql.js 全库导出改为 `node:sqlite` 的 WAL 增量写。界面（批次二）与检查点引用化仍未包含。

## 修复（全部来自 1.4.0-beta.1 的真实运行）

- **验证必有终结记录**：`run_verification` 被预算耗尽、取消或存储故障打断时，必定产出一条终结记录（先持久化 → 发 `verification_finished` → 写工作流检查 → best-effort 检查点 → 再抛出），失败以结构化 `verification_runtime_error` 记录。此前检查会永远停在 pending，模型只能看到"一直在跑"。验证审批的等待时长改为该运行剩余时长预算，不再使用固定 15 分钟 broker TTL。
- **分析模式的受控探针**：新增运行时 `probe` 工具，在 `<临时目录>/harness-agent-probe/<runId>`（仓库之外）执行一次性命令，影响记为 `probe` 且不递增仓库版本；授权按程序作用域，同一程序的后续探针不再逐条审批（此前一次分析被 4 次高风险审批打断）。权限策略本身没有放松：任意 `terminal` 仍按既有策略审批。
- **持久化**：见下。

## 存储

- `SQLiteFile` 改用 `node:sqlite`（WAL）。实测每次事件约 22KB 日志；那次真实运行的 143 次检查点由"每次重写 648MB（≈92GB 写盘）"降为约 50MB。进程崩溃不再丢失已提交数据。
- 同步接口不变，`HarnessDatabase` 与调用方零改动；干净关闭会折回日志并清掉 `-wal`/`-shm`，仍是单文件，便于备份与复制。
- 证据查询改为 `tool_evidence(run_id, call_id, sequence)` 索引 + `getToolEvidence`；`read_evidence` 不再每次解密整个 run。
- 旧库兼容：用真实 sql.js 写出的数据库可由新引擎打开，会话、标题、记忆、检查点与证据都保留。

## 打包构建修复

- tsup 默认剥掉所有 `node:` 前缀（`removeNodeProtocol`）。对 `node:fs` 无害，但 `node:sqlite` 是只能带前缀的内置模块，剥离后会去找一个不存在的 npm 包 `sqlite`：这样打出的 daemon 会在加载持久化时死亡，桌面主进程同样打不出可用产物。已在 `apps/daemon/tsup.config.ts` 与 `apps/desktop/tsup.config.ts` 设为 `removeNodeProtocol: false`，并由 `tests/bundle-140.test.ts` 守住（撤掉开关即变红）。
- 该缺陷**不是**单元测试能发现的：测试直接跑 TypeScript 源码，只有审计打包字节才暴露。本次就是打包内容审计拦下的。

## 验证

- `pnpm run typecheck`、`pnpm run lint`、`pnpm run test`（49 文件 / 297 用例）、`pnpm run build` 全部通过。
- 打包内容审计（对 `win-unpacked` 实跑）：app/渲染器/daemon 版本号一致；批次一标记 + 本轮三个修复标记共 **19/19**；sharp PNG 编码正常；daemon 语法检查通过；daemon 产物中已无 sql.js wasm 引用。
- **在打包运行时内实跑 WAL 往返**：`PRAGMA journal_mode` 返回 `wal`，写入一行、关闭、重开读回成功。
- **打包 daemon 端到端启动**（按桌面端相同方式，使用一次性数据目录）：`daemon listening on \\.\pipe\harness-agent-v2-…`，`health` 返回 `{status: "ok", version: "1.4.0-beta.2"}`，并在数据目录生成 `harness.sqlite` + `-wal`/`-shm`。这正是 beta.1 里 `connect ENOENT` 失败的那一步。
