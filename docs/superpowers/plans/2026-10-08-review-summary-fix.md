**审核截断、重复结论与输出额度设置修复方案（2026-10-08）**

目标：保留工作流自身的审核过程与完成门槛。Profile 未设置额外审核时，不增加额外审核要求，也不因这项配置缺失报错。应执行的审核中断时，保留当前有效的主模型报告并显示真实状态，避免再次生成同一份长结论。补上可编辑、可持久化、实际生效的最大输出 token 设置。

2026-10-09 实施状态：配置、审核预算/有限重试、有效报告复用和终态投影已实现；保留工作流固有审核。审查补充了“工作区变更同时耗尽预算时清除过时终态报告”的回归。最终构建与安装包验证记录见对应发布说明。

1. **已确认的原因与修复边界**

   - 主流程输出上限为 393,216 token，实际会按上下文余量缩小；本次问题发生在另一套独立审核预算中。
   - `packages/core/src/independent-review.ts:15` 的默认公式为 `min(8192, max(1024, 需求数 × 200))`。本次 4 项需求仅获 1,024 token，日志记录输出和推理用量均为 1,024，审核随后被截断。
   - `packages/core/src/engine.ts:1039` 捕获审核错误后设置停止原因；`finally` 调用 `finishStoppedRun()`，后者再次调用 `promptSummary()`，产生第二份长结论。审核 JSON 本身没有作为长回答展示。
   - 桌面端 `dedupeFinalText()` 将“原结论＋新增状态”视作重复而整体丢弃，可能同时丢掉“审核未完成”的提示。只修后端跳过总结不够。
   - Profile 的真实字段是 `verificationPolicy.reviewPolicy`，可选值为 `standard` / `risk_based`；缺失默认 `standard`，界面含义为“不额外启用”。现代工作流自身的独立审核由 `LightweightWorkflow.requiresIndependentReview = needsChange` 决定，顺序工作流继承该门槛。这是工作流固有审核，不能因 Profile 未配置就关闭。
   - 旧 `CodingWorkflow` 的需求核对、最终审查属于主流程门槛；它的额外独立审核由 Profile 风险策略触发。当前引擎仅有一个 `reviewChanges` 调用通道，现代流程并没有另跑一遍 Profile 审核；不能把这次重复结论解释成两个审核器各输出一次。
   - 最大输出 token 目前只存在于模型请求参数中：主流程及技能任务硬编码 393,216，审核另用内部预算。Profile、供应商持久化配置及设置表单均未贯通该字段；`maxContextTokens` 是上下文容量，不是最大输出额度。
   - 上次修复的历史停止指令清理继续保留。不删除历史事件，不扩大为整个工作流重构；新增输出配置时保留未设置情况下的兼容默认值。

2. **保留工作流审核，仅跳过未配置的额外审核**

   审核来源须明确区分，不能将“Profile 未启用”当成关闭所有审核的总开关：

   | 工作流与配置 | 行为 |
   | --- | --- |
   | 现代工作流修改任务，Profile 未设置或 standard | 原有需求核对、独立审核、失败修复及完成门槛全部保留；不新增 Profile 额外审核 |
   | 旧工作流，Profile 未设置或 standard | 原有主流程需求核对与最终审查保留；不执行可选独立审核 |
   | Profile 为 risk_based，但未命中风险条件 | 不新增可选审核；工作流固有审核照常 |
   | Profile 为 risk_based，且命中风险条件 | 执行适用的额外审核要求；已有同一证据版本的审核覆盖时沿用现有调用通道，不因来源有两种而重复调用 |

   - 保留 `LightweightWorkflow` / `SequentialWorkflow` 的固有审核门槛、`recordIndependentReview()`、需求和审核版本戳、失败诊断及验证要求；不因缺少 Profile 配置将其改为自动完成。
   - 原方案中“将所有未配置审核标记 skipped”“清除现代工作流审核待办”“修改默认强制审核测试以显式启用”的条款撤回。工作流自身的 pending/failed 审核不能标记成 skipped 或 passed。
   - 仅对未启用的 Profile 可选部分正常跳过；不产生配置缺失错误、不额外调用模型、不在最终答案追加错误提示。界面如显示该部分，可写“未启用额外审核”，避免与工作流审核状态混用。
   - `run-stop.ts`、`WorkflowProgress.tsx` 继续显示工作流固有审核及其未完成状态；只有不存在的 Profile 额外要求不得被误列为待办。
   - 恢复或续办保留原工作流审核语义，不借 Profile 缺省值绕过旧检查点的有效审核门槛。历史事件不重写。
   - 沿用现有 Profile 字段和当前审核调用通道，不新增必填审核模型配置，也不为两种审核来源盲目增加第二次模型请求。应执行的审核发生供应商错误、截断或缺少证据时，仍须如实处理。
   - 更新 `docs/agent-loop.md` 和设置帮助，明确现代工作流内置审核与旧流程可选审核的适用范围；不删除现代工作流已有的审核提示与要求。

3. **修收尾：复用提交审核的报告**

   修改 `packages/core/src/engine.ts`，在进入独立审核时冻结候选报告，记录报告正文、来源助手轮次、工作流 epoch/revision，以及工具活动和用户追加指令的版本。

   - 候选报告必须来自本次执行中最近一次成功结束、无工具调用、正文非空的助手轮次，并且属于当前证据和工作流版本。后续工具活动、新用户指令、修复或工作流失效均使候选不可复用。
   - 不使用全局 `if (finalText.trim()) return`：当前 `finalText` 会跨后续工具轮次保留，可能已经过时。
   - 审核运行失败且候选仍有效时，跳过 `promptSummary()`，以该报告及确定性的简短状态结束。结果保持 `review`，停止信息保留 `review_incomplete` 或实际预算停止原因。
   - 明确显示“独立审核未完成；以下报告尚未经独立审核确认”。正文中的模型自述“已完成”不能使界面显示为已审核通过。
   - 没有可复用报告时，保留现有的一次受预算约束的收尾总结；暂停或取消继续遵守现有规则。
   - 审核真实返回 `passed=false` 时，继续现有诊断/修复流程，不将其当成网络错误，不复用被否定的报告作为已通过结果。
   - 候选报告只在本次执行中有效；恢复旧检查点时不直接认领旧报告，需基于当前工作流重新确认。

4. **修审核预算，并限定截断重试**

   对工作流固有审核及适用的 Profile 可选审核均适用。`independent-review.ts` 保持单次调用职责；预算策略集中管理，重试由 `engine.ts` 调度。

   拟定自动策略：首次 `min(16384, max(8192, 需求数 × 400))`，明确输出截断后最多重试一次，将实际请求额度加倍、默认最高 32,768。本次 4 项需求的典型路径为 8,192 → 16,384。首次与重试均不得超过第 6 步配置的审核输出上限；这是待回归验证的应用默认值，并非保证所有模型都足够。

   - 所有额度包含推理与审核 JSON；保留推理，不借用压缩专用的关闭思考参数。
   - 请求额度还受完整请求的上下文估算、安全余量、费用和模型允许范围约束。协议目前没有模型最大输出能力字段；如增加 `capabilities.maxOutputTokens`，必须为可选字段，仅填入已确认的上限，旧配置继续兼容。余量不足时明确结束，不裁掉需求、diff 或证据以强行审核。
   - 仅捕获明确的 `ProviderOutputTruncatedError` 触发扩额度重试。真实 `passed=false`、无效 JSON、缺失证据、越权工具调用、超时和取消都不触发这类重试。
   - 重试使用同一份完整证据重新生成审核结果，不拼接两次截断 JSON。重试额度无法高于首次额度时直接停止。
   - 每次请求都计模型轮次并检查剩余费用；两次审核共用原有 60 秒总截止时间和任务截止时间，重试不能重新获得 60 秒。
   - 每次尝试分别记录额度、用量、推理用量、耗时和失败类型，失败用量也进入总账。供应商未报告用量时保留未知标志，并按可用估算预留重试费用。
   - 两次仍失败或预算不够时，进入第 3 步的简短失败收尾，不能为了避免重复而绕过工作流固有审核或已启用且应执行的额外审核。
   - 保留逐项需求证据校验及审核 JSON 的长度保护；输出 token 增大不等于放宽判定标准。

5. **修展示：同一份报告只显示一份，状态必须保留**

   修改协议、桌面端 `conversation-stream.ts` / `assistant-messages.ts`，并检查 Web 端对应投影。

   - 为新 `result` 事件增加可选的来源助手轮次引用，按 runId 与轮次 sequence 精确关联已流式展示的报告。
   - 终态到达时，以 `result.text` 和结构化状态更新对应报告，而不是再追加整篇；审核状态显示在报告附近，不能只藏在过程区。
   - 不用全文相似度删除内容，也不把所有较早助手文本当成重复。审核发现问题后产生的修订报告、工具前说明和用户要求的多版本内容须保留。
   - 对没有来源引用的旧事件保留兼容路径：完全重复可去重；同一末尾轮次的“原文＋状态后缀”合并展示并保留后缀；无法明确归属的不同文本不自动删除。
   - 事件存储和完整内容查看仍保留原始记录；实时显示、切换会话和重新打开历史应投影出一致结果。覆盖 `session.view` 预览到完整事件补载、事件分页重放，不能在补载后重新出现第二份终态正文。

6. **补上最大输出 token 设置**

   - 在 Profile 设置中增加“单次主回答最大输出 token”和“单次审核最大输出 token”。主回答留空沿用 393,216 的兼容默认值；审核留空使用第 4 步的自动策略，并展示当前默认上限。配置的是每次请求额度，不是整段会话的累计 token。
   - 在 Profile 协议中增加可选的生成额度配置（拟为 `generationPolicy.maxOutputTokens` / `reviewMaxOutputTokens`），贯通输入校验、保存/读取、配置导入导出、桌面表单和引擎；使用正整数校验，空值代表默认值。旧 Profile 不要求补填。
   - 每个新运行冻结生效配置到 RunSpec；正在执行的请求不受中途设置修改影响。界面说明保存后用于新运行；恢复已有运行沿用其冻结值，缺字段的历史运行使用兼容默认值。
   - 主流程、委派运行及使用该 Profile 的技能任务接入统一额度解析，移除散落的 393,216 常量。审核使用单独的审核上限，不再被主回答设置掩盖；上下文压缩继续保持自己的预算用途。
   - 实际请求额度取用户设置、已知模型输出能力上限、当前剩余上下文空间三者的最小值。模型最大输出能力与用户额度是不同字段；目前能力信息缺少输出上限，只能新增可选字段记录已确认值，未知时不能伪造。
   - 审核自动扩额度不能突破用户设置的硬上限；例如审核上限设置为 8,192，则首次最多 8,192，不能再自动请求 16,384。没有更高可用额度时不进行相同截断请求的重试。
   - 设置界面明确区分“上下文容量”“最大输出”和“任务轮次/费用预算”。请求诊断记录配置上限与实际发送上限，便于说明为何某次输出额度低于设置值。

7. **回归验收与交付顺序**

   | 场景 | 必须观察到的结果 |
   | --- | --- |
   | 现代工作流修改任务，Profile 缺省或 standard | 固有审核照常执行，未通过不能完成；无 Profile 缺配置错误、无第二次额外审核 |
   | 旧工作流，Profile 未启用额外审核 | 自身需求核对和最终审查保留，可选独立审核请求为零 |
   | risk_based 未命中或命中风险条件 | 只影响适用的额外要求，不改变工作流固有审核，不重复调用同一审核 |
   | 旧检查点固有审核 pending，恢复时 Profile 未启用额外审核 | 固有审核仍须执行；不得误标 skipped 或自动通过 |
   | 修改输出设置后保存、重启、启动新任务 | 值持久化且请求实际使用；主回答和审核额度相互独立 |
   | 审核额度设为 8,192 或模型剩余上下文不足 | 首次和重试均不超配置/上下文上限；正在运行的请求配置保持稳定 |
   | 主报告完成，审核成功 | 一份报告、审核通过；无额外主模型总结请求 |
   | 首次审核推理耗尽额度，第二次成功 | 只重试审核；两次用量和轮次均计入；最终一份报告 |
   | 两次审核均截断或无预算重试 | 一份原报告＋明确的审核未完成状态；不生成第二篇长总结 |
   | 审核真实发现问题 | 保留失败判定并进入修复流程，不能扩预算重试以求通过 |
   | 仅有旧报告，之后发生工具操作或用户追加指令 | 不复用旧报告；使用当前证据收尾 |
   | 无候选报告、暂停、取消、耗尽总时限 | 各自保持正确状态；不越过预算或取消边界 |
   | result 比流式正文多一段失败提示 | 原报告只显示一次，新增提示完整可见 |
   | 实时显示、历史重放、恢复旧检查点 | 内容与状态一致，旧停止指令不会重新生效 |

   测试落点：`tests/audit-review.test.ts`、`tests/workflow-audit.test.ts`、`tests/sequential-engine.test.ts` 等引擎集成测试、`tests/runtime-summary.test.ts`、`tests/loop-control.test.ts`、`tests/output-context-budget.test.ts`、Profile 协议/保存/设置表单测试、停止信息测试、桌面 `WorkflowProgress.test.tsx` / `conversation-stream.test.ts` / `assistant-messages.test.ts`，以及受影响的 Web/协议投影测试。保留现代工作流默认必须审核的现有断言，新增 Profile 缺省情况下仍保留该流程的回归。

   实施顺序为：确认并保留工作流审核边界 → 有效报告复用与失败状态 → 输出配置贯通与审核预算/有限重试 → 展示关联与历史兼容 → 定向测试、类型检查和相关 lint → 全量测试、构建及打包冒烟。用模拟供应商重现“1,024 token 全被推理占用”的事件序列，不重跑用户工作区里的实际操作。
