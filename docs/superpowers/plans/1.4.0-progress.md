## Review fixes applied on top of the batch

- `packages/core/src/pi-agent-bridge.ts`: `contextPolicy.workingContextTokens` needed
  `| undefined` under `exactOptionalPropertyTypes`, which was the only failing typecheck.
- Unconfirmed execution effects were silently cleared by the next read. `effect: "unknown"` is now
  sticky until a successful repository recheck or a confirmed write, and `compareWorkspace` records
  any observed content difference as a repository write even when a snapshot is incomplete, so a
  real edit can no longer escape the repository revision.
- `verify()` reported a missing verification configuration by aborting the whole run; it now returns
  a structured `verification_config_missing` item and keeps the remaining items running.
- `z.toJSONSchema` must be called with `{ io: "input" }`. The output-mode schema marked every
  defaulted field as required, and the wire-layer validation therefore hard-rejected the natural
  `read_file { path }` call; `search_files`, `todo` and `run_verification` were affected as well.
- Runtime-owned tool exemptions are driven by declared risk plus an explicit
  `ToolDefinition.selfAuthorized` marker instead of a hardcoded name allowlist.
- Observations are bounded instead of unbounded on the modern path (32 legacy, 512 schema v3).
- A thrown tool failure carried no result reference: pi turns the exception into a bare error
  message, so the model lost the `evidenceId` pointer that structured failures already had. The
  modern path now returns the same envelope and the failed call stays retrievable through
  `read_evidence`; the legacy path still throws on purpose.

## Live acceptance run against the packaged pre-release

- 2026-09-10: the plan's analysis prompt (`检查memory模块，分析得出可优化方案`) was run in the installed
  `1.4.0-beta.1` on real models, routed as `openai-compatible / deepseek-v4-flash`. It reached 22
  model turns and 38 tool calls with a 92.3% input-cache hit rate over 19/19 reported requests
  (553,089 input tokens, 510,592 cached) and made no repository change (`修改版本 0`), so the analysis
  stayed read-only as required. Estimated cost stays unknown rather than zero.
- The run exposed two runtime defects, both fixed here:
  - `verify()` could publish `verification_started` and then escape (budget, cancellation or a storage
    failure) without ever publishing `verification_finished`, so `localCheck`/`broaderCheck` kept
    their default `pending` for the rest of the run. The model read that as a harness-level "running"
    state, burned two self-correction attempts on it and ended the analysis through raw `terminal`
    calls that each needed a high-risk approval.
  - The interactive approval a verification needs was waited on with a flat 15-minute broker TTL that
    ignored the run's own duration budget, so an unanswered approval could outlive the run it belongs to.
- Fixed in `packages/core/src/engine.ts`: `verify()` now wraps the check loop and always publishes one
  terminal run (persist, emit `verification_finished`, record on the workflow, best-effort checkpoint)
  before rethrowing, and `authorizeTool` accepts an approval TTL that the verification path bounds by
  the remaining run duration. `tests/engine-modern-140.test.ts` adds the regression; it fails without
  the engine fix (`verification_started` 1, `verification_finished` 0) and passes with it.
- Root cause of the underlying abort, not fixed here: the daemon process died while exporting the
  entire `harness.sqlite` (648 MB) for a checkpoint, leaving `harness.sqlite.5836.tmp` behind and no
  daemon socket, which froze the run and produced the UI's `connect ENOENT` error. Every checkpoint
  still rewrites the whole database; that is the stage-6 redesign listed above as not started.
  Superseded on 2026-09-10 by "Incremental persistence" below: the write path no longer copies the
  database at all.
- 2026-09-10 gates after the fix: `pnpm run typecheck` clean, `pnpm run lint` clean,
  `pnpm run test` 47 files / 287 tests passed, `pnpm run build` succeeded.

## Controlled probes in analysis mode (the second live finding)

- The same run also showed what the plan's stage 1 was for: the analysis needed temporary
  experiments (a one-off interpreter script over stdin, a file-count query, the project's own test
  subset) and there was no sanctioned way to run them. In analysis mode `before()` rejected every
  non-read tool, so the `probe` effect the plan defines was unreachable, and the model fell back to
  raw `terminal` calls, each `high` risk in auto mode: four interactive approvals interrupted one
  analysis. The plan's constraints were kept exactly — line 14 "keep the existing permission checks,
  do not downgrade arbitrary terminal commands to read-only" and line 41 "arbitrary scripts still
  execute under the existing permission policy".
- Implemented without touching that policy:
  - A runtime-owned `probe` tool on the modern path (available wherever `terminal` is) that runs one
    bounded command inside an isolated probe directory, `<temp>/harness-agent-probe/<runId>`, outside
    the repository, so scratch artifacts can never look like a repository change.
  - `ExecutionEffect` now really produces `probe`: a probe that leaves the repository untouched is
    recorded as `probe` rather than `read` and never bumps the revision, while the before/after
    content comparison still runs so a probe that changes tracked content stays a `repository_write`.
  - Analysis mode admits non-destructive probes and still refuses raw `terminal` and repository
    writes: the plan's "reads plus controlled probes".
  - The probe's approval is scoped to the program instead of the exact arguments, so one approval
    covers further probes starting with the same program in that run and another program asks again.
    This is the deliberate answer to the four interruptions.
  - `authorizeTool` accepts a runtime-owned tool's definition and an explicit grant scope, so a
    runtime tool no longer fails with `Unknown or disabled tool`.
- Regression coverage (47 files / 290 tests, was 287): an analysis probe runs from the isolated
  directory, is recorded as `probe` with revision 0 and the run still completes; two probes of the
  same program raise exactly one `approval_required`; a probe that edits a tracked file is still
  detected as a repository write; the per-request tool set now includes `probe`. Reverting the three
  source files turns four of those assertions red.
- 2026-09-10 gates after the probe work: `pnpm run typecheck` clean, `pnpm run lint` clean,
  `pnpm run test` 47 files / 290 tests passed, `pnpm run build` succeeded.

## Incremental persistence: replacing the sql.js whole-database export (stage 6)

- The daemon death above was not a caught exception but a process-level kill: 143 checkpoints x a full
  648 MB export. No engine change can survive that, so the write path itself was replaced.
- `packages/persistence/src/sqlite.ts` now backs `SQLiteFile` with `node:sqlite` in WAL mode instead of
  sql.js. Every method stays synchronous, so `HarnessDatabase` and its callers are unchanged.
- Measured: about 22 KB of log per appended event, so the same run moves roughly 50 MB instead of
  having rewritten 648 MB per checkpoint. A clean close folds the log back
  (`wal_checkpoint(TRUNCATE)`) and drops the sidecars, so a closed database is still one file that can
  be copied or backed up. `writeFlushes` now counts only explicit checkpoints and must stay at 0 while
  writing, which is what the regression asserts.
- Evidence lookup is indexed: `tool_evidence (run_id, call_id, sequence)` is written as events are
  appended and exposed as `getToolEvidence(runId, callId)`. A pre-index database backfills lazily for
  the requested run only. `read_evidence` now uses it instead of decrypting every event of the run on
  each call; that is the one engine edit and it kept the existing `tool_finished` guard, so its
  behaviour - including `evidence_not_found` - is unchanged.
- Two real regressions were found by existing tests, not by review: `synchronous = FULL` fsynced every
  boundary write and pushed `loop-convergence`'s 128-tool-call case past its 5 s timeout (WAL's
  standard `NORMAL` fixed it, and it is still crash-safe against a process crash), and the workflow
  fixture keeps its database inside the workspace, so the new `-wal`/`-shm` files became large binary
  untracked files that made the real `git_diff` permanently `truncated`, which in turn stopped
  `diffRevision` from advancing until the repeated-observation guard ended the run (`db.sqlite*` is now
  excluded). Cross-checked by `git stash`-ing the persistence source and re-running those files against
  the sql.js engine: 26/26 and 19/19 passed there, which is what proved the failures came from this
  change.
- Legacy data: a fixture written by the real sql.js engine (same schema and AAD strings, no evidence
  table) opens under the new engine and keeps its session, title, memory, checkpoint and evidence; a
  separate process that commits and exits without closing keeps its row across a reopen.
- Not done here: checkpoints still carry the full transcript (their size is unchanged - storing
  references is the next step), messages and large outputs are not yet content-deduplicated, stream
  deltas are not yet batched to 100 ms / 4 KiB, and the runtime migration steps (backup, staged
  migration, integrity and count validation, atomic switch, rollback) are not implemented. Details and
  limits: `.cache/upgrade-1.4.0/storage-report.md`.
- 2026-09-10 gates after the storage change: `pnpm run typecheck` clean, `pnpm run lint` clean,
  `pnpm run test` 48 files / 294 tests passed, `pnpm run build` succeeded.

## The packaged build rewrote Node's own module names (found while packaging beta.2)

- Assembling the beta.2 installer, the packaged-content audit refused to pass: the daemon bundle did
  not contain `node:sqlite`, even though no test failed. tsup removes the `node:` prefix from every
  built-in import by default (`nodeProtocolPlugin`, `removeNodeProtocol: true`) and marks the result
  external. For `node:fs` that is invisible because the unprefixed name also resolves, but `sqlite`
  is not a built-in name - it is a package that does not exist - so the shipped daemon would have
  died while loading persistence, and the desktop main bundle, which also packages persistence,
  would have failed to start. Verified in the packaged runtime: `require("node:sqlite")` works,
  `require("sqlite")` is MODULE_NOT_FOUND.
- Fixed with tsup's supported option, `removeNodeProtocol: false`, in `apps/daemon/tsup.config.ts`
  and `apps/desktop/tsup.config.ts`. `apps/cli` and `apps/gateway` do not package persistence (their
  bundles contain no sqlite reference at all), so they were left alone.
- Guarded by `tests/bundle-140.test.ts`: it asserts both configs disable the stripping and bundles a
  fixture through the daemon config, checking the output still says `node:sqlite`. Reverting the
  config turns it red with `import { DatabaseSync } from "sqlite"`.
- Lesson: `pnpm run build` succeeding and every unit test passing says nothing about the bundle.
  Tests run from TypeScript source, so only auditing the packaged bytes catches this class of defect.

## The approval dialog could not be answered (found in the live UI)

- Reported from the running app as "审批超出页面大小". The overlay is `position: fixed` with
  `display: grid; place-items: center` and no scrolling, and the panel had no height limit: when the
  dialog was moved from the old `.approval-dialog` (which carried
  `max-height: min(760px, calc(100vh - 56px)); overflow: auto`) to `BuiGlassPanel`, that guard was
  dropped. Measured with a 90-entry verification payload, the dialog grew to 10,489px inside a 712px
  viewport and pushed 拒绝/批准一次 off-screen with no way to reach them - so the run waits for a
  decision that cannot be given.
- Fixed by keeping the centering safe and bounding the dialog: `place-items: safe center` and
  `overflow-y: auto` on the overlay, `max-h-full flex flex-col overflow-hidden` on the panel, a
  scrollable body (`min-h-0 flex-1 overflow-y-auto`), and `max-h-[40vh]` on the command preview. The
  approvals tab had the same defect and worse: it rendered `JSON.stringify` of the raw input with no
  truncation at all, and now uses the same capped preview helper as the dialog.
- Verified by measurement rather than by eye. A harness in `.cache/approval-layout/` renders the old
  and the new markup against the built stylesheet in the real Electron Chromium and hit-tests the
  buttons: before, the approve button sat at y=10429 in a 712px viewport and `elementFromPoint`
  missed it; after, it sits at y=552 and is reachable without scrolling. It is not committed as a
  test - the repository has no DOM or layout test environment, so the measurement is a script.
- 2026-09-10 gates after the fix: `pnpm run typecheck` clean, `pnpm run lint` clean,
  `pnpm run test` 49 files / 297 tests passed, `pnpm run build` succeeded.

## Truncated model turns were reported as an opaque failure

- The live app surfaced `Responses stream did not complete: {"reason":"max_output_tokens"}`. That was
  two defects at once. The planner asked for 4096 output tokens on every main-loop request, which was
  the binding term of `min(8192, estimate, context x ratio)` - so the 8192 ceiling in the same
  expression was dead code - and the Responses adapter treated a truncated answer exactly like a
  failed request, printing the provider's raw JSON with no hint of what happened or what to do next.
- `estimatedOutputTokens` is now 8192 so the ceiling binds; the reserve ratio still protects models
  with a small context window. The adapter now separates `response.failed`/`error` from
  `response.incomplete` and reports the latter as a truncated turn that names the limit
  (`max_output_tokens`) and what to do about it.
- Both are pinned by tests: the analysis fixture asserts every main-loop request carries 8192, and
  the continuation test now expects a different error per failure mode (truncated, failed, EOF)
  instead of one shared regex. Reverting either source change turns its test red - `expected 4096 to
  be 8192`, and `Responses stream did not complete: {"...` for the incomplete case, which also
  confirms the old message was the raw dump the user saw.
- Left inconsistent on purpose: the Chat, Anthropic and Gemini adapters ignore their own truncation
  signals (`finish_reason: "length"`, `stop_reason: "max_tokens"`, `finishReason: MAX_TOKENS`), so
  there a cut-off answer silently looks like a finished one. The live route, DeepSeek Responses, was
  the broken one; the rest is recorded rather than changed.
- Related, not a defect: the same report included a failing `probe` whose output was a Python
  traceback (`AttributeError: type object 'ModelRequest' has no attribute 'model_fields'`). That is
  the model's own experiment hitting the pydantic v1/v2 difference inside the project it was
  inspecting, and the probe reported it exactly right - exit code, stderr, evidence id, isolated
  directory outside the repository.
