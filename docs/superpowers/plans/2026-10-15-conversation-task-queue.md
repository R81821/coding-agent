# 单对话工具并行与持久任务队列执行计划

- 日期：2026-10-15
- 状态：已完成；2026-10-15 源码、兼容迁移、测试、交互验证与构建验收通过，执行记录见第 9 节。
- 项目根目录：`D:/qweai`
- 目标：在一个主对话内，提高独立工具调用的并发效率，并持续管理、并行执行模型生成的多个 task。
- 方案：本地 SQLite 持久队列 + 单 daemon 调度器 + 有界工具执行池 + 现有子任务执行器。
- 本期不接入 Redis，不增加 Redis/BullMQ 依赖，也不开展多会话调度、多机器执行或跨机器迁移。

## 1. 完成后的行为

1. 主模型将可执行工作提交为结构化任务，队列根据依赖、优先级、资源和授权选择任务。
2. 多个独立 task 可以同时执行；一个任务释放槽位后，立即补充其他符合条件的任务，不要求无关的整批任务全部结束。
3. 单个 task 内，独立、只读且无共享状态冲突的工具可以并发调用；写入和有状态操作按资源互斥。
4. 主模型保持一个权威对话上下文，统一处理结果、集成补丁和验证，不同时运行多个主对话写入器。
5. 界面能准确区分等待、运行、待合并、完成、失败和暂停等状态；重新打开会话能够恢复队列记录。
6. 暂停、补充要求、继续和撤回继续保持现有语义，累计用量记录实际消耗。

需要准确区分：底层 `executeGraphTasks` 已经在一批任务内使用空槽补位；目前缺少的是高于单次 `run_tasks`/`delegate` 调用的持续持久队列。现有 `run_tasks` 等待本次调用的整批结果，新增任务和下一轮集成仍依赖模型后续调用。

现有 `beginTasks` 会在真正获取执行槽前把整批标记为 running。本次必须将“已接受排队”与“实际执行”分开。

## 3. 不可破坏的约束

- 单个主对话只有一个协调器更新主 transcript、工作流、事件序号和主检查点。工具执行可以并行，权威状态提交经过同一协调入口。
- SQLite 继续由同一 daemon 独占，子任务通过协调器提交状态，不各自打开同一个数据库文件。
- 并发策略不得扩大工具、文件、委派或外部服务权限。模型声明的 read 或 writePaths 不能替代运行时校验。
- 子任务执行成功不代表计划节点验证通过；后继仍遵守现有真实验证依赖，不能擅自降低门禁。
- 共享工作区的写入与不兼容读取互斥；独立写任务优先沿用隔离 worktree。父工作区的补丁集成串行执行。
- 不允许重启、超时或重试盲目重放结果不明的非幂等操作。
- 并发配置不改变模型的实际上下文容量、输出配置或摘要策略，不引入固定摘要 token 上限。
- 保持一个主上下文占用条。子任务消耗纳入总输入、输出、缓存和预算统计，但不叠加为主对话上下文占用。

## 4. 数据与状态设计

### 4.1 唯一状态源

新增 `conversation_tasks` 持久表，作为当前对话执行队列的唯一事实来源，不复用现有定时任务 `tasks` 表。

- 任务正文、结果摘要和敏感元数据沿用保险库加密；索引只保留调度需要的最少字段。
- 工作流中的 taskExecutions、todo 和界面列表作为该队列的兼容投影，不各自独立认领或改变任务状态。
- 检查点记录对应的队列版本和恢复所需引用。任务状态变化、相关事件与检查点关联应在同一 SQLite 事务中提交。
- 保留兼容旧检查点的读取与迁移路径，不将旧 completed 记录直接推断为已验证。

建议的任务字段：

| 字段组     | 内容                                                                |
| ---------- | ------------------------------------------------------------------- |
| 身份       | taskId、sessionId、parentRunId、stepId、planGeneration              |
| 来源       | 初始 run 请求，或明确的 steering messageId；保留来源检查点/队列版本 |
| 调度       | executionState、priority、dependsOn、blockedReason、createdAt       |
| 输入       | 任务说明、约束、相关证据 ID、上下游产物引用、上下文与工作区版本     |
| 资源       | read/write 模式、规范化文件范围、共享资源键、预算预留引用           |
| 执行尝试   | attemptId、childRunId、实际开始/结束时间、重试原因                  |
| 产物       | 摘要、证据引用、patch 引用、工作树与基线引用、集成回执              |
| 消耗与验收 | 实际用量水位、预留状态、独立的验收状态和验证回执                    |

队列长度与同时执行数分别限制；现有单批最多 8 个不能直接当作整个持久队列的长度限制。限额需要可配置、校验并明确展示，不能默默截断任务。

### 4.2 执行与验收分别记录

建议 executionState：`blocked`、`queued`、`running`、`awaiting_integration`、`completed`、`failed`、`interrupted`、`cancelled`。

- blocked：依赖、授权或输入尚未满足，记录具体原因。
- queued：已接受且等待资源槽位；只有实际认领并准备启动后才进入 running。
- awaiting_integration：子任务已产出结果，等待父任务集成或确认结果适用性。
- completed：执行和必要集成结束；是否通过验收仍以真实验证回执为准。
- interrupted：已启动但中断，需要检查实际状态；不能当作安全可自动重试的 queued。

验收沿用计划节点和验证回执。后继要求前置节点 verified 时，仅产生 patch 或子任务返回 completed 不会解锁后继。

每次重试分配新的 attemptId；任务身份、历次产物、真实消耗保留，避免覆盖历史和重复计费。

- [x] 调度器持续按依赖、优先级、关键路径、资源和预算补位，新入队的独立任务不等待上一批全部结束。

- [x] 父模型可集成已就绪的产物，并继续安排独立工作；最终验收仍等待所需任务、合并和真实测试完成。

### 阶段 4：暂停、继续、追加要求和撤回

- [x] 暂停先关闭派发入口，唤醒等待任务结果的主流程，再递归暂停已启动子任务；派发前再次校验暂停状态。
- [x] 保留安全收尾语义，等待已启动工具、子任务、工作树清理和快照结束后才发布稳定 paused。
- [x] 专门检查现有执行池只观察 AbortSignal、暂停不等于 abort 的边界，禁止暂停后空槽继续启动等待项。
- [x] 恢复前核对计划版本、依赖、工作区和执行结果；已确认完成的项复用，中断写操作先检查产物。
- [x] 新补充要求提升计划版本，重判未启动项；已运行旧任务的产物保留审计，由父协调器确认是否继续采用。
- [x] 消息撤回恢复点包含发送前的队列状态、尝试与预算账本水位；恢复与对话检查点在同一数据库事务中提交。
- [x] 撤回仅移除该消息之后产生的队列分支，保留此前任务和文件；文件恢复/数据库失败沿用现有补偿机制。
- [x] 清除迟到回调、运行尝试和 UI 缓存重新挂回已撤分支的可能性，提交前校验 taskId/attemptId/计划版本及撤回状态。

验收：暂停后没有新任务启动；暂停后立即发送、再次暂停再撤回，只恢复最新消息对应分支；完成消息仍不能撤回；旧分支结果不会重新进入上下文。

实际迁移采用追加建表，不复用定时任务表。旧嵌入式 `HarnessEngine` 未提供 `conversationTasks` 执行器时保留原同步委派契约；正常 `createRuntime` 已接入持久队列。单次 `run_tasks` 仍最多提交 8 个节点，连续提交共享同一队列和执行池；队列容量独立校验，超限明确报错。默认 task 并发 4、队列容量 80、工具并发 4、模型请求并发 4，可通过 README 和 `.env.example` 中的独立配置修改。

执行路径为 `blocked ↔ queued → running → awaiting_integration → completed`，失败或中断重试需要原因并创建新尝试。`running` 但没有实际 `startedAt` 时界面显示准备资源。验收另由当前真实父验证回执推进；普通读取回执不能充当写任务的补丁集成回执。崩溃或撤回后若发现此前等待任务实际启动过，会保留为中断，不能直接重新认领。

`reopen_step` 也推进队列计划代次；已完成任务保留为旧代次审计，新工作获得新的任务与尝试身份，不能凭旧完成记录去重掉重新打开的节点。

阶段 0 核对确认：原 `executeGraphTasks` 已能在单批内补位，本次新增的是跨调用的持久队列；`beginTasks` 保留为旧协议路径，正常 runtime 的排队与运行由持久队列投影。工具、task、模型请求分别限流；一个父引擎入口负责主 transcript、事件序号和检查点提交。并发配置没有更改实际上下文容量、输出配置或摘要策略。
